## 1. Requirements

Stated by the developer:

- **R1 Extensible.** Future extensions add node types, value types and edges.
  A document says which extensions it needs, as a list of requirements.
- **R2 Music only.** A document holds the music.
  It holds no graph-backend details (rustworkx indices, adapter names)
  and no Python or library details (module paths, class layout, slots, `_id`).
  Someone who re-implements OMK in another language,
  keeping the names and data types,
  can read and write the same documents.
- **R3 Specified.** We publish a specification good enough for that re-implementation.
- **R4 Ids persist.** Every OMK-assigned UUID survives a round trip.
  Both nodes (`OmkObject._id`) and edges (`OmkEdge._id`) have one.
- **R5 Exact round trips.** Each direction of a round trip gives back exactly what went in
  (stated precisely as laws in §6).

What follows from those:

- R2 and R3 together mean **the specification is the source of truth, not the Python.**
  A type's JSON field names are spec names.
  Renaming a dataclass field must not quietly change the format,
  so no codec is generated by reflecting over dataclass fields (§5.3).
- R5 needs a **canonical text form**:
  one byte sequence per graph, whatever the backend, insertion order or language.
  "Identical output" cannot be checked otherwise.
- R5 also means **`==` cannot be the test for a round trip.**
  Several value types compare equal while holding different data (§2.4).
- R1 together with R2 means the extension mechanism is a **property of the format**
  (namespaced type names plus declared vocabularies).
  It is not a Python plugin system,
  although the Python side needs some way to supply codecs for an extension (§5.3).

## 2. Findings that shape the design

### 2.1 What exists

- `OmkGraph` has six stubs, all `NotImplementedError` (`src/openmusickit/graph/graph.py:100-155`):
  `from_json`, `import_json_graph`, `export_to_json`, `export_json_to_file`,
  and the `.json` branches of `import_file` and `export_file`.
  `_plans/completed/consistency-audit.md` settled these names.
- `io/` holds one format per subpackage (`io.musicxml`).
  Its docstring says a format module may know one musical system well.
  JSON belongs there too.
- `_plans/musicxml.md` §5.11 promised that `meta["musicxml"]` would stay "JSON-friendly".
  It is not quite (§2.5).
- `_plans/formal-specification.md` scopes a *behavioural* spec (laws, conformance kits).
  This plan is a *data* spec: it says what a document contains, not how operations behave.
  So it does not wait on that plan's open question 1 (whether transposition goes on the ABC).
  It does answer that plan's question 4 for the format:
  the format is versioned by vocabulary versions, separately from the library.

### 2.2 The node and edge model

- Every node is a slotted, mutable dataclass.
  No node field holds another `OmkObject`, so every relationship is an edge.
  That makes a flat document possible: a node list and an edge list.
- Ids are `init=False`.
  The reader has to set `_id` after construction, as `graph._fork` already does (`graph.py:2315`).
- **The edge class carries information that `EdgeType` does not.** *(verified)*
  `OmkEdge(type=NEXT) != Next()`.
  `add_edge(a, b, t)` always builds a plain `OmkEdge`, so a plain NEXT, BRANCHES or CONTAINS edge can exist.
  A Score's CONTAINS edges are plain on purpose; a LineGroup's are timed `Contains` edges.
  The format has to tell these apart (§9, D3).
- `EdgeType` is a closed `StrEnum`.
  **An extension cannot add an edge relation to the Python model today**
  (`USER_DEFINED` takes no name).
  The format can leave room for namespaced relations now (§4.4).
  Changing the model is a separate decision (§10).

### 2.3 Systems have no identifiers

`TonalSystem` and `TemporalSystem` are frozen value dataclasses, `(name, description, universal)`.
There is no registry,
and two of them share the name "Western Standard Music Notation" (tonal and temporal).
Value classes hard-code their system through a property,
so a type tag already implies it.
`SyncLine.temporal_system` is the only stored reference to a system.

Writing a system out as its three fields would put prose into data:
editing `CLOCK_TIME.description` would make every old file decode to a system
that is not equal to `CLOCK_TIME`,
and `compatible_with` would then fail.
**Systems need stable identifiers that a vocabulary declares** (§4.3).

### 2.4 Where `==` hides data the format must keep

From the inventory; the starred items are *(verified)*:

- `Measurable` compares by length.
  So 4/4 equals 2/2 (TimeSignature presentation)*,
  a dotted quarter equals `TemporalUnit(3, eighth)`,
  a triplet ratio equals a sextuplet one*,
  every `GraceDuration` equals `ZeroDuration`*,
  and `ClockDuration(2)` equals `ClockDuration(Fraction(2))`*.
- `TemporalRatio` and `Tempo` compare by multiplier.
  `Tempo(120, quarter) == Tempo(60, half)`*,
  and a `Tempo` equals the plain `TemporalRatio` with the same multiplier.
- `ToneCollection` ignores `name_template`.
  `ChordType` ignores `quality` and `suffix`; `Chord` ignores `suffix`.
- `TonalVector` compares equal to a plain tuple,
  and `KeySignature` cannot tell `1`, `1.0` and `Fraction(1)` apart.

Every one of these fields is stored, so every one is written (§4.5).
Round-trip tests compare structure, never `==` (§7).

### 2.5 Things the format cannot carry as the model stands

- **Floats in values.** *(verified)*
  `ClockDuration.from_seconds(1.5)` stores `microseconds=1500000.0`.
  `KeySignature` accepts any `Real`, so `KeySignature(f=0.5)` holds a float.
  A float cannot round-trip exactly across languages,
  and it decodes into the wrong Python type if it comes back as a rational.
- **`Fraction`s in `meta`.** *(verified over all ten fixtures)*
  `meta` is otherwise plain JSON (dict, str, list, bool, int, None; no floats, no tuples).
  The exception is 184 `Fraction`s under `meta["musicxml"]["offset"]` and `["end_offset"]`
  on `Marking` and `MarkSpanner`.
- **Symbol identity.** *(verified)*
  `io.musicxml` checks marks and bar lines with `is`, in 17 places
  (`mark is scoring.tie`, `shape is scoring.start_repeat`, ...).
  A `Mark` decoded from JSON is equal to `staccato` but is not `staccato`.
  So a score that goes MusicXML → JSON → MusicXML would lose its ties,
  pedals and repeats **without any error.**
  This is not JSON's bug; JSON would only make it more common.
  `copy.deepcopy` and `pickle` also make new, equal symbols,
  and so does `OmkGraph.materialize`, which forks content with `deepcopy`.
  *(verified 2026-11-02)* A deepcopy of the Schubert fixture exports
  0 `<tie>` elements instead of 188.
  The code is also inconsistent with itself:
  `mark in tables.NOTATION_SPAN_NAMES` is a dict lookup, which compares with `==`.
- **Shared `Word`s.** `parse_lyrics` gives every syllable of a word the same `Word` object.
  JSON gives each syllable an equal copy.
  Nothing relies on the sharing (no `word is` checks).
  The format does not carry this, and the spec says so.

## 3. The shape of a document

A small example: one C quarter note with a staccato.
Ids are shortened here; real ones are full lowercase UUIDs.
This is the canonical text: keys sorted, two-space indent (§4.6).

```json
{
  "edges": [
    {
      "@id": "5d1e…",
      "@source": "a0c4…",
      "@target": "e93b…",
      "@type": "Edge",
      "origin": "asserted",
      "relation": "marks"
    }
  ],
  "format": "omk-json",
  "graph": {
    "description": null,
    "info": {},
    "name": "Sketch"
  },
  "nodes": [
    {
      "@id": "a0c4…",
      "@meta": {},
      "@type": "Marking",
      "mark": {
        "@type": "Mark",
        "aliases": [],
        "attachment_mode": "single",
        "binds": false,
        "description": "…",
        "kind": "articulation",
        "name": "staccato"
      }
    },
    {
      "@id": "e93b…",
      "@meta": {},
      "@type": "NoteEvent",
      "duration": {
        "@type": "wsmn:MetricalDuration",
        "denominator": 4,
        "dots": 0,
        "numerator": 1,
        "ratio": null
      },
      "tones": [
        {"@type": "wsmn:TonalVector", "chromatic": 0, "diatonic": 0, "octave": 0}
      ]
    }
  ],
  "vocabularies": {
    "omk": {"uri": "https://openmusickit.org/spec/omk", "version": "0.1"},
    "wsmn": {"uri": "https://openmusickit.org/spec/wsmn", "version": "0.1"}
  }
}
```

(The real canonical form puts every object on separate lines.
The one-line objects above are only to keep the example short.)

Why the `@` keys:
structural keys (`@id`, `@type`, `@meta`, `@source`, `@target`) can never collide with a field name.
Fields really do include `type`, `kind` and `section_type`.
Also, `@` sorts before every letter, so sorted keys put the structural ones first,
and a reader sees what an object is before what it holds.

## 4. The format

### 4.1 Envelope

| key | content |
|---|---|
| `format` | the literal `"omk-json"`, so a reader can recognise the file |
| `vocabularies` | prefix → `{uri, version}`: the requirements list (R1) |
| `graph` | `GraphMeta`: `name`, `description`, `info` |
| `nodes` | node objects, sorted by `@id` |
| `edges` | edge objects, sorted by `@id` |

`vocabularies` lists exactly the vocabularies the document uses, and always includes `omk`.
"Uses" means a type, system or relation from that vocabulary appears in the document.
The writer works the list out from the content,
so the list is deterministic.

### 4.2 Vocabularies

A vocabulary is a published, versioned set of type, system and relation names.
Each one has its own spec page.

- `omk` is the core:
  every node type, the edge kinds,
  and the values that belong to no system
  (`SilentTone`, `ZeroDuration`, `GraceDuration`, `ClockDuration`, `TemporalUnit`,
  `CompoundTemporalUnit`, `TemporalRatio`, `Tempo`, `ToneCollection`, `Mark`,
  `TempoTerm`, `Word`).
  Core names are written without a prefix.
- `wsmn` is Western Standard Music Notation:
  `TonalVector`, `MetricalDuration`, `TiedDuration`, `TimeSignature`, `Chord`, `ChordType`,
  `Key`, `KeySignature`, `ModePattern`, `StaffClef`, `BarLineShape`, `BracketShape`,
  `PercussionTone`.
  WSMN lives in this repo, but it is opt-in like any other system
  (the package docstring says "nothing here assumes one"),
  so it gets its own vocabulary.
- An extension (OMK Gregorian, say) publishes its own vocabulary,
  and its names appear as `gregorian:Neume`.

The **URI** identifies a vocabulary.
The prefix is local to the document, as XML namespace prefixes are,
so the reader matches on the URI.
For a deterministic output, each vocabulary declares a preferred prefix and the writer uses it;
two loaded vocabularies with the same preferred prefix are a writer error.
(This is decision D4.)

**Versions** are `major.minor`.
A reader accepts a vocabulary with the same major version
and a minor version no higher than the one it implements.
While a version is `0.x`, the minor version must match exactly,
because breaking changes are allowed.
Both vocabularies start at `0.1`.
Declaring `1.0` is the commitment described in `formal-specification.md` under "What it would cost afterwards",
and it is the developer's decision to make.

### 4.3 Identifiers for systems

A vocabulary declares identifiers for its systems:
`omk` declares `any` and `clock-time`;
`wsmn` declares `wsmn:tonal`, `wsmn:metrical` and `wsmn:percussion`.
Tonal and temporal identifiers are separate namespaces, because the field type says which one is meant.
`SyncLine.temporal_system` is written as the identifier string.
Writing a system that no loaded vocabulary declares is an error,
such as an ad-hoc `TemporalSystem("Mine", ...)`.

### 4.4 Nodes and edges

**Nodes** have the keys `@id`, `@type`, `@meta`, then the fields of that type.

**Edges** have the keys `@id`, `@type`, `@source`, `@target`, `@meta`, then their fields.
The edge kind follows the model's classes, which are also OMK's concepts:

- `Next`: `origin`
- `Branch` and `Simultaneous`: `origin`, `anchor`, `displacement`
- `Contains`: `origin`, `displacement` (its anchor is always the onset)
- `Edge`: `origin`, `relation`. This is the plain `OmkEdge`, including a Score's CONTAINS.

`relation` is an `EdgeType` value (`"marks"`, `"contains"`, ...).
The format allows a prefixed relation (`"gregorian:ligature"`),
so that extension relations need no format change once the model supports them (§10).
(This is decision D3.)

### 4.5 Values and primitive types

Every value is either a primitive or a tagged object (`@type` plus fields).
**Every stored field is written, with `null` for `None`, and default values are written too.**
Leaving out defaults would tie the format to defaults that can change.
Fields that are derived rather than stored are never written
(`Chord.name` is formatted from `name_template`; `LyricSyllable.text`; `StaffClef.reference_tone`).
Fields with `compare=False` are written, because they are stored.

Primitive types in the spec:

- string, boolean, null
- **integer**: a JSON integer
- **rational**: a JSON integer if the value is a whole number,
  otherwise the string `"n/d"` in lowest terms with a positive denominator.
  The format never uses a float in a musical value.
- **uuid**: lowercase, hyphenated, 36 characters.
  Any UUID version is allowed, matching `_plans/completed/small-items.md`.
- **enumeration**: a string from a list the spec gives.
  For a `StrEnum` this is its value (`"rim shot"`).
  `RelativePitch` is an `IntEnum`; the spec gives it the strings `"low"` … `"high"`.
- **array of T**: a tuple field, kept in order
- **set of T**: an array sorted by the canonical bytes of each element.
  Today `NoteEvent.tones` is the only one.
- **system identifier**: see §4.3
- **json**: `meta` and `info` only.
  Any JSON value, except that a float must be finite and is written in canonical form (§4.6).

Some example encodings:

- `TonalVector` has `diatonic` and `chromatic`, and an `octave` that is null for a two-coordinate vector.
  Two coordinates and three are different values.
- `MetricalDuration` is written as stored after normalisation:
  `numerator`, `denominator`, `dots`, `ratio`.
- `Tempo` is `count`, `beat`, `clock_time`, which is its constructor's signature, not the `TemporalUnit` pair it stores.
  A plain `TemporalRatio` is written as `nominal` and `contextual`.
- `ChordType` leaves out `root`, because the constructor forces it to `(0, 0)`.

**Values are written in full, never by symbol name.**
`staccato` is written as its six fields, not as `"staccato"`.
A document then stands on its own,
a re-implementation needs no copy of OMK's symbol tables,
and editing a table later never changes what an old file means.
The cost is size: every `ModalContextEvent` repeats a seven-tone mode.
(This is decision D2.)

### 4.6 Canonical text

- UTF-8, no BOM, LF line endings, a final newline.
- Object keys sorted by Unicode code point.
- Two-space indentation.
  Separators are `,` then a newline between items, and `": "` between a key and its value.
  An empty array is written `[]` and an empty object `{}`.
- Strings and numbers are written as RFC 8785 (JCS) writes them,
  which is ECMAScript `JSON.stringify` style:
  only `"`, `\` and control characters are escaped, using the short forms where they exist and `\u00xx` (lowercase) otherwise.
  A lone surrogate is an error.
  A float, which can occur only in `meta`, uses ECMAScript shortest round-trip formatting.
  Python's `repr` differs from it (`1e+16` against `10000000000000000`),
  so the writer needs a small formatter.
- Nodes and edges are sorted by `@id`.
  Set-typed fields are sorted as §4.5 says.

The writer is a hand-written canonical dumper of about 60 lines,
not `json.dumps(sort_keys=True, indent=2)`.
Its output is close to that call's,
but the float and escaping rules have to match the spec exactly,
and a dumper written straight from the spec doubles as its reference implementation.

Sorting by id gives an order that looks random.
In return it is stable under edits (adding a note adds one block to a diff),
it is trivial to specify,
and it works for fragments, cycles and graphs with no Score.
A musical order (walk the scores, then the lines) reads better,
but it is hard to specify for incomplete music.
(This is decision D9.)

### 4.7 What a reader accepts and checks

- The reader accepts any valid JSON layout: any key order, any whitespace, nodes in any order.
  Only the writer is bound to the canonical form.
- It **rejects** a document that is not `format: omk-json`.
- It rejects an object with duplicate keys.
  Python's `json` silently keeps the last one, so the reader parses with an `object_pairs_hook`.
- It rejects a vocabulary it was not given, or a version it does not support.
  The error names the URI and the version.
- It rejects an unknown `@type`, relation or system identifier,
  and a value outside its spec domain.
  For example, `TonalVector` diatonic must be 0–6 and chromatic 0–11,
  even though the Python constructor does not check (decision D12).
- It rejects a duplicate node or edge id, and an edge whose endpoint is missing.
- The graph's own rules are enforced by inserting through the adapter:
  one edge of a type per ordered pair, and NEXT at most one in and one out.
  The reader does not impose the semantic methods' further rules
  (for example, that a branched head has no incoming NEXT),
  because `OmkGraph.add_edge` does not impose them either.
  A document can hold anything a graph can hold, no more and no less.
- Errors are a new `OmkJsonError(OmkError, ValueError)`, modelled on `MusicXmlError`.

### 4.8 What a writer refuses

The writer raises `UnexportableError` (which already exists) and names the object for each of these:

- a node, edge or value whose **exact** class has no codec.
  The writer looks up the exact class and never uses `isinstance`;
  otherwise an unregistered subclass of `Part` would be written as a `Part` and lose its data.
- a float in a rational field
- a `meta` value that is not plain JSON
  (a tuple, a `Fraction`, a key that is not a string, NaN).
  A tuple would come back as a list and break R5.
- a system with no identifier (§4.3)

`ContextEvent` and `DivisionEvent` have no `duration` field in the spec.
After P4 the model refuses a non-zero duration on them, so the writer does not check for one.

## 5. Where it lives in the code

### 5.1 Package

`src/openmusickit/io/omk_json/`.
It is not `io.json`, because `from openmusickit.io import json` would shadow the standard library's name in the caller's namespace (decision D11).

- `canonical.py`: the canonical dumper, and a parser that rejects duplicate keys
- `primitives.py`: rationals, uuids, enumerations
- `vocabulary.py`: `Vocabulary` and `TypeCodec` (§5.3)
- `core.py`: the `omk` vocabulary's codecs
- `wsmn.py`: the `wsmn` vocabulary's codecs
- `document.py`: the envelope; `dumps`, `loads`, `write`, `read`

The WSMN codecs live in `io/`, not in `systems/wsmn/`,
so that domain classes never learn about any storage format (AGENTS.md).
An extension package ships its own vocabulary module in the same way.

### 5.2 Public API

```python
from openmusickit.io.omk_json import dumps, loads, read, write

text = dumps(graph)                      # canonical str
graph = loads(text)                      # new OmkGraph, ids kept
write(graph, "score.omk.json")
graph = read("score.omk.json", vocabularies=[GREGORIAN])
```

The `OmkGraph` stubs are then filled in:

- `from_json(text)` and `export_to_json() -> str` take and return text, not a dict,
  because the canonical form is text.
- `export_json_to_file(f)`.
- `import_json_graph(text)` adds the document to an existing graph.
  It keeps the ids, and refuses with `GraphError` if any id is already on the graph, adding nothing.
  (`add_node` silently does nothing for an id that is already present,
  so without this check a collision would quietly merge two objects.)
  As its docstring already says, the document's `GraphMeta` is not merged.
- `.json` dispatch in `import_file`, `from_file` and `export_file`.
  The suggested suffix is `.omk.json`; `Path.suffix` reports it as `.json`.

Vocabularies are an **explicit argument** with a default of `(CORE, WSMN)`;
the core is always included.
They are not discovered through entry points or a global registry,
because AGENTS.md prefers explicit parameters to hidden global state.
If a caller forgets the extension, the result is a loud `OmkJsonError` that names the missing URI.
Entry-point discovery can be added later without changing the format (decision D10).

How the graph gets built:
`document.py` decodes the text into `(GraphMeta, nodes, [(edge, source_id, target_id)])`,
and a private `OmkGraph` method inserts them through `self._graph`.
That keeps adapter access inside `OmkGraph`,
as `fork_graph` in the tests does by hand.
Ids are set as `_fork` sets them, by assigning `_id`.

### 5.3 Codecs

```python
@dataclass(frozen=True, slots=True)
class TypeCodec:
    name: str                                   # spec name, e.g. "TonalVector"
    cls: type
    encode: Callable[[Any, Encoder], dict]      # fields only; Encoder recurses into values
    decode: Callable[[dict, Decoder], Any]

@dataclass(frozen=True, slots=True)
class Vocabulary:
    prefix: str
    uri: str
    version: str
    types: tuple[TypeCodec, ...]
    tonal_systems: Mapping[str, TonalSystem]
    temporal_systems: Mapping[str, TemporalSystem]
```

There is one explicit pair of small functions per type, about 45 types in all.
They are deliberately **not** generated from `dataclasses.fields`:
if they were, the spec would really be defined by the Python field names (§1).
A field-coverage test (§7) catches a field added to a class but not to its codec.
This is the minimum machinery R1 needs;
nothing here goes beyond what it takes to load a codec table supplied by an extension.

## 6. Round-trip laws (R5, made precise)

- **L1, document → graph → document.**
  For every canonical document `d` that the reader accepts, `dumps(loads(d)) == d` byte for byte.
- **L2, graph → document → graph.**
  `loads(dumps(g))` has the same node ids and edge ids as `g`,
  the same endpoints for every edge,
  the same exact class for every node, edge and value,
  stored fields that are structurally identical (not `==`, see §2.4),
  and equal `meta` and `GraphMeta`.
  It is therefore also `is_equivalent` to `g`.
- **L3, independence.**
  `dumps(g)` depends only on the content, the ids and the meta.
  It is the same on `RustworkxAdapter` and on `tests/graph/dict_adapter.py`,
  and the same whatever order the nodes and edges were inserted in.
  This is the test that proves no backend detail leaks into the format (R2).
- **L4, canonical.**
  Parsing the output and dumping it again with the canonical dumper gives the same bytes.

Python distinctions the format deliberately does not carry,
so L2's "structurally identical" ignores them:

- a whole-number `Fraction` comes back as an `int` (the number is the same);
- shared `Word` instances come back as equal copies (§2.5).

The spec states both.

## 7. Tests

These follow AGENTS.md's testing section.
The finite domains get exhaustive sweeps, the unbounded ones get Hypothesis.

- **Value sweeps** (exhaustive, finite domains).
  Every in-domain `TonalVector` from `tests/domains.py`,
  every `Mark`, `TempoTerm`, `ChordType`, `ModePattern`, `StaffClef`, `BarLineShape` and `BracketShape` in the symbol tables,
  and every `PercussionTone` and enumeration member.
  Each must decode to a structurally identical value of the same class,
  and re-encode to the same bytes.
- **Graph properties** (Hypothesis): L1–L4 over a new `any_graphs()` strategy in `tests/strategies.py`.
  It must cover every node class, edge kind and value type, plus random JSON `meta`.
  (`exportable_scores` is limited to what MusicXML can carry, so it is not enough.)
  For L3, the same document is loaded into both adapters, and also loaded with its node and edge lists shuffled.
- **Field coverage.**
  For each codec, the stored dataclass fields of its class (less `_id` and `meta`)
  must equal the fields the codec writes, plus any documented derived or omitted field.
  Every concrete `OmkObject` subclass, edge class and value class in the core and in `systems/wsmn` must have a codec.
  This keeps the spec, the codecs and the classes from drifting apart.
- **Corpus.**
  For each of the ten fixtures: MusicXML → graph → JSON → graph.
  The result must keep the ids and meta and be `is_equivalent`,
  and **writing MusicXML from the reloaded graph must give the same document as writing it directly.**
  That last check is the test for the symbol-identity problem in §2.5.
- **Golden documents.**
  The spec's example documents are files under `docs/spec/examples/`.
  The tests load each one and require `dumps(loads(x)) == x`, so the spec and the code cannot drift.
- **Errors.**
  One test per refusal in §4.7 and §4.8.
- **Schema.**
  The writer's output for the corpus and for Hypothesis graphs validates against the published JSON Schemas.
  This needs `jsonschema` as a dev dependency (decision D8).

Two existing helpers are close but not right here.
`tests/graph/helpers.py:snapshot` ignores edge ids on purpose,
and its `repr`s print sets in iteration order.
L2 needs a new structural comparison helper.

## 8. Prerequisites (model changes; each one a separate commit)

All four were confirmed with the developer on 2026-11-02.

- **P1a `ClockDuration` rejects floats.**
  `microseconds` and `from_seconds`, `from_minutes` and `from_milliseconds` are already typed `int | Fraction`,
  but a float is stored without complaint *(verified)*.
  Construction raises `TypeError` for a float (in `__post_init__`, which every constructor passes through).
  `tests/systems/wsmn/temporal/test_metrical_duration.py:1079` uses `from_seconds(1.5)`
  and becomes `from_seconds(Fraction(3, 2))`.
- **P1b `KeySignature` alterations are `int | Fraction`.**
  The type changes from `Real`, and floats are rejected with `TypeError`.
  A quarter-tone sharp is `f=Fraction(1, 2)`.
  The docstring's microtone line says so, and `tests/systems/wsmn/tonal/test_key.py:136` and `:195`
  change from `f=0.5` to `f=Fraction(1, 2)`.
  This settles D5: floats leave the model instead of the writer refusing them.
  The writer still refuses a float in a rational field, as a backstop for extension types.
- **P2 `==` instead of `is` for symbols in `io.musicxml`, at all 17 sites**
  (13 in `writer.py`, 3 in `reader.py`, 1 in `tables.py`; `grep -nE ' is (not )?scoring\.'`).
  Symbols are values, and values compare by equality.
  None of the 238 marks, 14 bar lines, 19 clefs or 4 bracket shapes is equal to another,
  and no two marks share a name *(verified)*,
  so `==` matches exactly what `is` matched.
  It also fixes the existing deepcopy and materialize bug (§2.5).
  Tests:
  a regression test that a deepcopied fixture exports the same document as the original (ties included),
  and a table test that the symbols in each table are pairwise unequal,
  so that a future entry cannot collide.
  Rejected:
  making symbols keep their identity through copies (it does not fix JSON or hand-built marks),
  interning in the JSON reader (it fixes JSON only, and the reader would need WSMN's tables),
  and comparing by name (a custom mark named "tie" would pass for WSMN's).
- **P3 `meta["musicxml"]` offsets as strings.**
  The reader stores `offset` and `end_offset` as `str(fraction)` (`"1/4"`, `"-3/8"`, `"2"`;
  `reader.py:1972-1973`).
  The writer already reads them with `Fraction(meta.get("offset", 0))`,
  and `Fraction` parses those strings, so the writer does not change.
  Every `meta` in the corpus is then plain JSON.
  The reader's docstring for the meta keys says so.
- **P4 Zero-duration events stay zero.**
  `MeterEvent().duration = quarter` is accepted today, and so is the same on `DivisionEvent` *(verified)*.
  The existing `SequentialEvent.__setattr__` guard is extended so that assigning anything but a `ZeroDuration`
  to a `ContextEvent` or `DivisionEvent` raises `ValueError`.

Run the heavy test set (`uv run pytest --hypothesis-profile=thorough -m ""`) before P1a, as the baseline.

## 9. Decisions for the developer

The recommendation comes first in each.

- **D1 Is `meta` in the document?** **Confirmed 2026-10-21.**
  *Yes, under `@meta`, as plain JSON.*
  `meta` is not music, but it is not a backend or Python detail either.
  It is consumer data that OMK models on purpose.
  Without it, a JSON round trip loses `meta["musicxml"]`, and the MusicXML export afterwards changes.
  The alternative is music only, with no `meta` and no `GraphMeta.info`.
- **D2 Symbols written in full, or by name?** **Confirmed 2026-10-21.**
  *In full* (§4.5).
  By name gives smaller, friendlier files,
  but the spec then has to include OMK's symbol tables as normative data,
  and editing a table changes old files.
- **D3 How edges are encoded.** **Confirmed 2026-10-21.**
  *By kind (`Next`, `Branch`, `Simultaneous`, `Contains`, and `Edge` + `relation`)*, which mirrors the model with no change to it.
  The alternative is `relation` plus an optional timing block,
  with `add_edge` changed to build `Next` for NEXT, so that a plain NEXT cannot exist.
  That is a model change and the more musical format,
  but it still needs some marker to tell a Score's plain CONTAINS from a group's timed one.
- **D4 How vocabularies are identified.** **Confirmed 2026-10-21.**
  *By URI, with a document-local prefix* (§4.2).
  The alternative is short names drawn from a list OMK curates:
  simpler, but third-party names can collide,
  and adding URIs later would break the format.
  The URIs need a domain: `openmusickit.org` appears, commented out, in `pyproject.toml`.
  The URIs are identifiers and do not have to resolve yet.
- **D5 Floats.** **Confirmed 2026-11-02:** change the model (P1a, P1b).
- **D6 Unknown vocabularies.** **Confirmed 2026-11-02.**
  *Refuse, and name what is missing.*
  The alternative is to carry unknown nodes through as opaque objects,
  which needs a new `OmkObject` kind. Defer it until someone needs it.
- **D7 Where the spec lives.** **Confirmed 2026-11-02.**
  *`docs/spec/` on the Quarto site*:
  `omk-json.qmd` (data model, primitives, envelope, canonical form, conformance, versioning),
  `vocabulary-omk.qmd`, `vocabulary-wsmn.qmd`,
  `schema/*.schema.json` (JSON Schema 2020-12),
  and `examples/*.omk.json`.
  Pages are executable, so the build round-trips every example.
  The alternative is a top-level `spec/`, separate from the docs build.
- **D8 JSON Schema and `jsonschema`.** **Confirmed 2026-11-02.**
  *Publish schemas, and add `jsonschema` to the dev group.*
  A schema cannot express the canonical form or the graph rules,
  but it gives a re-implementer something to check structure against mechanically.
- **D9 Node order.** *By id* (§4.6), or a musical walk order.
  **Deferred to Stage 3:** dump one fixture in both orders and decide from real files.
- **D10 How vocabularies are supplied.**
  *An explicit argument* (§5.2), or entry-point discovery.
- **D11 Module name.** *`io.omk_json`*, or `io.json`.
- **D12 Value domains checked on read.** **Confirmed 2026-11-02.**
  *Yes.*
  A spec domain that the reader does not enforce is not really part of the spec.
  This makes the reader stricter than some Python constructors (`TonalVector` does not validate).
